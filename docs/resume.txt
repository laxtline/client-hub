5. INTERVIEW TALKING POINTS (be ready to explain these)
-------------------------------------------------------------------------------
Q: How does authentication/authorization work?
A: JWT issued on login (bcrypt-hashed passwords, 10 salt rounds). Middleware
   verifies the token — with the algorithm pinned to HS256 so an attacker can't
   substitute a differently-signed token — and re-fetches the user from the DB
   on each request, so a deleted or disabled account loses access immediately.
   A separate role middleware guards routes per role.

Q: What is "tenant isolation" and where is it enforced?
A: Every controller that can return client data resolves the caller's own Client
   record from their user id and filters by it. The UI also hides what a client
   can't use, but that's cosmetic — the security boundary is server-side. A
   client hitting /api/projects/<someone-else's-id> gets a 403, not data.

Q: Why verify the payment webhook on the server?
A: The browser can be tampered with, so an invoice is only marked "paid" after
   Razorpay's HMAC signature is verified against the RAW request body. That's
   why the webhook route is mounted BEFORE express.json() with a raw parser —
   re-serialising the JSON would change the bytes and break the signature. The
   handler is also idempotent, because gateways retry webhook deliveries.

Q: What happens if the AI API is down or rate-limited?
A: The AI summary service catches the error, logs it, and returns a deterministic
   template built from the same aggregated stats, flagged riskFlag: "unknown" so
   the UI can label it honestly. The feature degrades instead of failing. Every
   external integration in the app follows that same pattern.

Q: How is progress calculated?
A: A pure function computes (done tasks / total tasks) as a percentage. It's
   isolated from the database so it's trivial to unit-test, and it's reused by
   the project list, the project detail page, and the AI aggregation step.

Q: What did you do about performance?
A: Three things with measurable results. Route-level React.lazy plus a dynamic
   import for socket.io took the initial bundle from ~748 kB to ~233 kB, so
   recharts and dnd-kit only download on the pages that use them. The client
   search box is debounced, which turned one API call per keystroke into one per
   search. And the API gzips responses while nginx gzips static assets.

Q: How would you scale / deploy this?
A: The API is stateless, so it sits behind a load balancer with managed
   PostgreSQL (Neon/Supabase). Socket.io needs a Redis adapter to broadcast
   across instances. The frontend is static and goes on a CDN (Vercel). It's
   already containerized with docker-compose for local parity, and /api/health
   reports database reachability so a load balancer can drain a bad instance.

Q: What did you do for code quality?
A: 44 Vitest tests covering pure logic, auth, the RBAC middleware, the error
   handler and the webhook signature check; ESLint + Prettier with a flat config
   running at zero warnings; and a GitHub Actions pipeline that runs lint, tests
   and build for both apps on every push and pull request.

Q: Tell me about a bug you found and fixed.
A: (Pick one you can talk through.) The Socket.io server was configured with
   origin '*' plus credentials: true — browsers reject that combination, so
   real-time notifications would have silently failed in production while
   working fine locally. Another: dnd-kit fires a click on pointer-up after a
   drag, so dropping a Kanban card also popped its detail modal open; the fix
   was to track whether the gesture became a drag and swallow that click.
