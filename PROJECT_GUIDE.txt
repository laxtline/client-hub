ClientHub file notes

I kept this longer guide because it helps me find the code when I come back to it. README.md is the shorter starting point. These notes cover the actual files, including local configuration names, but don't copy secret values.

The code is split into client, server and python-services. React pages call an API wrapper, Express checks the request, and Prisma reads/writes PostgreSQL. Python is only the optional summary service. Nothing here needs Next.js.

I added the current account files to the tree below so I can find them while tracing a login. I don't count the contents of node_modules, __pycache__, .git or virtual environments. node_modules holds installed packages; Python caches are generated; a virtual environment holds Python packages. Any protected docs directory is left alone. CLIENTHUB-docs is a separate sibling folder.

Folders

.qodo - Local tool folders; the app does not read them.
.qodo/agents - Local tool folders; the app does not read them.
.qodo/workflows - Local tool folders; the app does not read them.
.vscode - Stores workstation editor preferences. It is not part of the deployed application.
client - the independently installed React and Vite frontend, its configuration and browser tests.
client/src - browser application source. main.jsx mounts the application and App.jsx assembles its providers.
client/src/api - Keeps HTTP calls separate from screens. All feature clients share axiosClient and its authentication handling.
client/src/components - Groups reusable UI by feature so pages can assemble small components instead of duplicating markup.
client/src/components/common - shared buttons, inputs, dialogs, feedback, branding, pagination and error UI.
client/src/components/dashboard - reusable summary cards and charts for project and revenue information.
client/src/components/invoices - invoice creation, invoice lists, PDF downloading and the labelled demo payment confirmation.
client/src/components/kanban - the task board, status columns, draggable task cards and task detail/comment dialog.
client/src/components/layout - the authenticated page shell, navigation and frontend route guards.
client/src/components/notifications - the notification bell, notification list and read-state interactions.
client/src/context - Keeps application-wide authentication, socket, theme and toast state through React Context.
client/src/hooks - reusable access to contexts, request state, debounced input and invoice refresh events.
client/src/pages - complete screens selected by the browser URL, including authentication, dashboards and business records.
client/src/routes - Maps browser URLs to screens and role guards. These are frontend routes, not Express API routes.
client/src/utils - shared display, date, role and escaping helpers used by several screens.
client/tests - Playwright browser tests. These exercise the application through Chromium rather than mocking React.
python-services - Groups services implemented in Python separately from the JavaScript frontend and main API.
python-services/ai-service - the optional FastAPI summary service, its dependencies, container definition and local configuration.
python-services/ai-service/tests - two pytest tests for health and template fallback behavior.
server - the independently installed Node and Express API, Prisma configuration and deployment entry points.
server/api - the Vercel function entry point. This path imports Express without starting the long-lived socket/cron server.
server/scripts - account setup and guarded integration/account checks. These run from a terminal, not as public HTTP routes.
server/src - the main API source, long-lived server entry point and all feature layers.
server/src/config - Creates shared clients and configuration for the database, uploads, payments and environment checks.
server/src/controllers - Handles HTTP requests, checks resource ownership, invokes services or queries Prisma and shapes responses.
server/src/jobs - Defines in-process scheduled jobs for summaries, overdue invoices and token cleanup.
server/src/middleware - authentication, role checks, validation, request limits and centralized error handling.
server/src/prisma - the PostgreSQL schema, seed program and an old SQLite file. The active schema does not use that SQLite file.
server/src/routes - Maps API paths and HTTP verbs to validation, authorization and controller functions.
server/src/services - reusable invoice, payment, summary, email and notification operations.
server/src/sockets - Attaches Socket.io to the long-lived HTTP server and emits events to authenticated user rooms.
server/src/utils - calculations, PDF generation, sanitization, logging and webhook signature verification.

The files

.env
Root settings used by Compose interpolation. This is separate from the API dotenv file. Setting names: GROQ_API_KEY, GROQ_MODEL, IMAGEKIT_PRIVATE_KEY, IMAGEKIT_PUBLIC_KEY, IMAGEKIT_URL_ENDPOINT, JWT_SECRET, RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET, SMTP_FROM, SMTP_HOST, SMTP_PASS, SMTP_PORT, SMTP_USER, VITE_RAZORPAY_KEY_ID.

.gitattributes
Git line endings and binary/language hints. It is not repository history.

.gitignore
Keeps secrets, dependencies, builds and local data out of a new commit.

.vscode/settings.json
One local VS Code Python terminal preference. It is not runtime setup for other machines.

LICENSE
The MIT license for the project.

client/src/api/authApi.js
The login, signup, session and change-password requests live here. They use axiosClient for tokens and cookies. The old forgot/reset request methods still point to the API, but those endpoints now return administrator-contact guidance with 403.

client/src/api/axiosClient.js
Adds the access token and sends the refresh cookie. I coordinate refresh requests within this tab and give each waiting request the same user/token result. An eligible 401 gets one refresh attempt. Password-change requests handle their own auth error. Separate tabs can still race on the shared cookie.

How I'd read it

Start with the schema, then index.html -> main.jsx -> App.jsx -> AppRoutes. Follow Login and authApi into authRoutes/authController. After that, follow a project/task request, then invoices and payments. Read the token/payment transactions before trying to explain duplicate handling. What happens on a request

A page calls an API wrapper. axiosClient adds the token and sends cookies. Express checks the current session, workspace access, role and request data. The handler then applies linked-client ownership or team assignment scope. Prisma talks to PostgreSQL and the response updates the page. PDF downloads return bytes rather than JSON. Some saved events also create notifications and go through the user's socket room.

The payment UI is a local simulation and production blocks it. Real checkout isn't finished. Summary fallbacks are intentional. Task moves save status/history, but don't broadcast task:updated. The normal server starts sockets/jobs; the Vercel app export doesn't. Those are easy details to forget during a demo.

Getting it running

How I set up ClientHub from scratch

I run PostgreSQL in Docker and the apps in separate terminals. That is the route to use for now; the full application Docker build still needs fixes.

Before starting

Install Git, Node.js 22 (or a compatible supported version), Docker Desktop and Python 3.12 if you want the summary service. The older Python packages can warn on newer interpreters. Check node --version, npm --version, docker --version and py -3.12 --version. RTK is only an optional command wrapper on my machine, not an app dependency.

The current copy is D:\Projects\On Working Projects\CLIENTHUB. On another machine, clone your own repo and use that path instead. Repo URL: NOT FOUND - please fill in.

Local settings

If they don't already exist, copy server/.env.example to server/.env and client/.env.example to client/.env. Don't overwrite your existing settings. Fill the values in privately.

The API needs DATABASE_URL and JWT_SECRET. CLIENT_URL must match the browser origin; NODE_ENV controls things like production cookies and the payment simulation block. PORT can be set for the API. The browser uses VITE_API_URL and VITE_SOCKET_URL. The normal local addresses are listed below; PROJECT_GUIDE.txt lists all setting names.

Node dotenv normally reads server/.env when I start it from server. It doesn't pick every .env.local/.env.production file automatically. Root .env is for Compose interpolation. Vite has its own mode/override rules, and its VITE values are public browser settings. Don't put a private key there.

Start the database

In PowerShell:
  Set-Location -LiteralPath 'D:\Projects\On Working Projects\CLIENTHUB'
  docker compose up -d postgres
  docker ps --filter name=clienthub-postgres

Docker Desktop has to be running. Compose publishes PostgreSQL on local port 5433 and keeps its data in a named volume. Use the development database details from docker-compose.yml when setting DATABASE_URL privately. If the port is busy, check what's already running before changing anything or removing data.

Start the API

In a new terminal:
  Set-Location -LiteralPath 'D:\Projects\On Working Projects\CLIENTHUB\server'
  npm ci
  npm run prisma:generate
  npm run prisma:push
  npm run seed
  npm run accounts:setup
  npm run dev

npm ci already generates Prisma through postinstall. For a fresh database, run prisma:push and seed before accounts:setup. Account setup creates a public demo user, so doing it before the first seed would make the seed skip the agency sample records. For an existing database, stop the API, run npm ci and npm run accounts:setup, then restart it. Check the intended database and stop on an unexpected data-loss prompt. Do not force a reseed for this update.

Check http://localhost:5000/api/health. A 200 response should say database ok. A 503 means the database isn't reachable, even if Node itself started. API routes use http://localhost:5000/api.

  Set-Location -LiteralPath 'D:\Projects\On Working Projects\CLIENTHUB\client'

  npm run dev

Open http://localhost:5173. I keep localhost consistent across the browser/API setup so cookies and allowed origins don't get confusing. If Vite picks a different port, check the conflict and update the origin deliberately.

Stopping and fixing basic problems

Ctrl+C stops each app terminal. From the root, docker compose stop postgres stops the database without deleting its volume.

For login trouble I check API health, the seeded account and the origin settings first. For missing Prisma code I run npm ci/generate from server. Forgotten passwords are now handled by an administrator; SMTP is only needed for optional notification emails. Summary fallbacks can come from missing config, Python being down or the Node/Python timeout mismatch. Production rejecting the mock payment is expected. None of these needs a forced database reset as the first fix.

Words I keep seeing

API is the interface between the browser and server. A controller handles a request; a service holds logic that can be reused. Middleware checks/processes the request before the handler. Prisma is the ORM between my code and relational tables. A foreign key links records. A transaction saves related changes together or rolls them back.

A JWT is a signed access token, not encrypted private storage. A refresh token gets a new access token. A webhook is a provider calling my server. Idempotency means a retry shouldn't repeat the business effect. Socket.io handles the live connection. Cron is a time schedule, but my in-process job only works while the process runs. A migration is a versioned database change; db push doesn't create that history.

How login and account setup work now

I use four role strings: admin, team_member, client and demo. A staff title such as Project Manager is just a label in the sample data, not an extra permission role.

Public signup and the shared demo

Signup only creates a demo user. Sending role=admin or team_member in the request does not grant agency access. After signup or a later login, the visitor lands at /demo and sees an empty workspace with zero projects, tasks and invoices. The page makes no business-data requests. The API rejects demo reads and writes with 403, and Socket.io rejects demo connections too.

The login page shows demo@clienthub.example / Demo@ClientHub123. It also has the normal email/password form and a Create a demo account link. I do not show the role-specific seed passwords on this login screen. Those sample logins are documented in README.md for a local role walkthrough.

There are two different meanings to keep straight. A public account has role demo and cannot read agency records. A fictional seed account keeps its admin/team/client role, but has isDemo set so its shared password stays locked. The flag does not turn a seeded admin into an empty demo user. Neither public demo nor seeded shared passwords can be changed or reset.

Creating a team account

Admin opens Team & Accounts and enters the member's name and email. The API generates a temporary password, stores its bcrypt hash and returns the temporary login once. createdByAdmin is true and mustChangePassword is true. The screen keeps those returned details only in memory; the admin shares them privately with the owner.

The new member signs in through the common login form. Before showing any work, the app opens Set your new password. The backend blocks workspace APIs until this is done, so opening another URL does not skip it. After a successful change, the member goes to /team, which shows the Team Dashboard and their assignments.

Creating a client account

Admin creates the client from Clients with a required contact email. The server creates the client-role login and linked Client record in one transaction. If the email is already taken, the operation fails without leaving half a client behind. The generated temporary credentials are shown once, just as for team accounts.

The client sets a personal password on the first login and then goes to /client. The API resolves that account's linked Client record. The user can read its own projects, tasks, invoices, PDFs and summaries, and comment on its own tasks. Another client's IDs do not grant access. Clients cannot edit staff task fields or create agency records.

What team can read and change

Team sees projects that contain tasks assigned to that user. The project response only includes their own tasks and the client identification needed for that work. It removes project budgets, invoices and full client details. Team cannot open the client directory, admin account list, agency revenue dashboard, invoices, payment history or summaries.

Admin creates/assigns tasks using the project form or task dialog. Team can change permitted work fields, status, hours and comments on its assigned tasks. It cannot reassign tasks or create its own assignment. Removing the assignment removes access, including direct task/comment/activity requests. The backend checks the assignee again when updating team work.

Forgotten passwords and later changes

The common login page says: Account banwane ya password reset karwane ke liye apne agency administrator se contact karein.

For a managed team/client account, admin uses Reset password in Team & Accounts. This generates another temporary password, sets mustChangePassword again and ends existing sessions. The owner must choose a personal password at the next login. Admin cannot view the previous password or recover it from the hash. A disabled account must be enabled before its password is reset.

A managed user who knows the current password can use Change password in the navbar. It checks that password and requires a different new one. New passwords must be at least eight characters and at most 72 bytes. The browser also asks for confirmation; the API checks the actual password rules.

Public /api/auth/forgot-password and /api/auth/reset-password return 403 with contact guidance. They do not send reset emails. Old /reset-password browser links lead to the same help page. SMTP is still used by optional notifications and scheduled mail, not by password recovery.

Sessions and account status

User has isDemo, createdByAdmin, mustChangePassword, disabled and sessionVersion fields. The API compares the access JWT's version with the current database value. Password changes, administrator resets and enable/disable actions increment sessionVersion, revoke existing refresh sessions and clear old reset-token entries. Existing access tokens then fail with 401. The normal server also disconnects the user's sockets; socket authentication checks current account state and token expiry.

Before the setup script runs, publicUser already treats an old untrusted team registration as demo. setup-accounts.js converts those old registrations to role demo and revokes their refresh sessions. Known seed accounts retain their sample roles and locked passwords. Accounts created through the current admin flow are preserved. This update does not delete clients, projects or invoices.

API paths I follow while checking this

POST /api/auth/signup - public demo registration.
POST /api/auth/login - common login; returns the user and access token, plus the refresh cookie.
POST /api/auth/refresh - rotates the refresh cookie and returns the latest account state.
GET /api/auth/me - current safe account details, without its password hash.
POST /api/auth/change-password - authenticated temporary/current password plus the new password.
POST /api/auth/logout - revokes the current refresh session and clears its cookie.
GET /api/accounts - admin-only team/client account list; no current passwords or saved temporary passwords.
POST /api/accounts/team - admin creates a managed team member.
POST /api/accounts/:id/reset-password - admin issues a new temporary password for a managed team/client.
PATCH /api/accounts/:id/status - admin enables/disables a team/client login using a boolean disabled value.
POST /api/clients - admin creates a client with its linked login and temporary credentials.

The account-management reset endpoint is for team/client accounts. It is not an administrator self-recovery endpoint. The admin can disable a login without deleting the user's business records. Demo, pending-password and non-admin sessions cannot call the account-management routes.
